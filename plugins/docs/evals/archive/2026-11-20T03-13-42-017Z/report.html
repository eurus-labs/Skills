# orderlog architecture overview

`orderlog` is a small Python package (`src/app`, about 75 lines) with three layers. Its README describes a CLI that records orders and reports on them. The code only implements recording, and nothing is persisted yet.

## Components

| Layer | Module | Role |
|---|---|---|
| **api** | `api/cli.py` | `main()` is the CLI entry point. It builds an `OrderService` and records every argument in `sys.argv[1:]` as a SKU. |
| | `api/http.py` | `Handler.post(body)` checks that `sku` is present, raises `ValueError` if it isn't, then records the one SKU. |
| **core** | `core/service.py` | `OrderService.record(skus)` creates an `Order` per SKU, passes each to the store, and returns the count. Its docstring says it owns no storage. |
| | `core/models.py` | Domain types: `Record` (base class with a `key` attribute) and `Order(Record)`, which has a `sku` and a `total()` method that returns `len(sku)`. |
| **infra** | `infra/store.py` | `Store` keeps orders in an in-memory list (`rows`) and `put()` appends to it. |
| | `infra/config.py` | `load()` returns `{"path": $ORDERLOG_PATH or "orders.json"}`. |

## Dependencies

Imports point inward, and there are no cycles:

```
api/cli.py ──┐
             ├─► core/service.py ─► core/models.py
api/http.py ─┘          │
                        └────────► infra/store.py ─► infra/config.py
```

- `api` imports only `core.service`.
- `core.service` imports `core.models` and `infra.store`. This means core depends directly on infra, with no interface between them.
- `infra.store` imports `infra.config`.
- `core.models` and `infra.config` import nothing from the project. The only third-party dependency is `os` from the standard library.
- `pyproject.toml` declares Python 3.9 or later and no runtime dependencies.

## Entry points

- **CLI:** `pyproject.toml` registers the console script `orderlog = app.api.cli:main`. `python -m app.api.cli` also works through the `__main__` guard.
- **HTTP:** `api/http.py:Handler.post` is a handler class only. No server, router or script entry point calls it, so it is currently unreachable from outside the code.

## Order flow

CLI path, `orderlog SKU1 SKU2`:
1. `cli.main()` creates `OrderService()`, which creates `Store()`. The store calls `config.load()`, so the settings are read at that point.
2. `service.record(["SKU1", "SKU2"])` creates one `Order(sku)` for each SKU.
3. `Store.put(order)` appends each order to `rows`.
4. `record` returns the count, and `main` returns `0`.

HTTP path, `Handler.post({"sku": "X"})`:
1. The handler checks that `sku` is present and raises `ValueError` if not.
2. It calls `service.record([body["sku"]])`, which follows steps 2–4 above and returns the count.

Each `Handler` and each CLI run builds its own `OrderService` and `Store`, so no state is shared between them.

## Gaps between the code and its stated intent

- **Nothing is persisted.** `Store` is memory-only, and the docstring says "until flushed", but no flush exists. The `path` setting is loaded and never used. When the CLI exits, the recorded orders are lost.
- **There is no reporting.** The README says the tool "prints them back", but there is no read or list method on `Store` or `OrderService` and no report command. `Order.total()` has no callers.
- **Input checking is only on the HTTP side.** The CLI passes raw `argv` straight through. The `http.py` docstring says it validates input "before anything else sees it", but the check covers only whether `sku` is present, not its type or value.
- **`Record.key` is unused.** It is a class-level `0` that nothing sets or reads.
