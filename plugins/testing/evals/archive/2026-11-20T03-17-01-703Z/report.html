## Suite summary
`tests/test_cart.py` has 8 tests, and the only file under `tests/`. pytest ran it in 0.01s and all 8 passed. The suite is not order-independent:
- `test_cart_state_after_earlier_tests` passes in file order, but fails alone with `assert 0 == 4`.
- It also fails when the file is run in reverse order, also with `assert 0 == 4`.
- I did not run a random order, because `pytest-randomly` isn't installed.

Most of the suite would still pass if `Cart` were badly broken. Only two tests could fail on a behavior change (items 4 and 6 below), and both are weak or fragile.

## Findings

### Blocking
1. **`tests/test_cart.py:12-14`** — `test_add` asserts only `result is not None`. `Cart.add` returns the new quantity for the SKU. A change that returned `0`, the wrong SKU's quantity, or `False` would still pass. Assert `CART.add("widget") == 1`, and use a fresh `Cart()` instead of the shared one.

2. **`tests/test_cart.py:17-19`** — `test_add_multiple` asserts `count() > 0`. If `add` ignored `quantity` and always added 1, the test would still pass. A total that was off by any amount would too. Assert the exact count (`== 3` on a fresh cart) and the return value of `add`.

3. **`tests/test_cart.py:22-24`** — `test_remove_returns_something` asserts `remove(...) in (True, False)`, which any boolean satisfies. Inverting `remove`'s return value, so it returned False for a present item, would pass. Nothing checks that the item is gone or that `count()` dropped. Assert `True` for a present SKU, then that `count()` fell by the right amount.

4. **`tests/test_cart.py:27-29`** — `test_count_is_an_int` checks only the type. A `count()` that always returned `0`, or that counted lines instead of units, would pass. Assert exact values after known adds, including that quantities sum across lines.

5. **`tests/test_cart.py:32-35`** — `test_apply_coupon` patches `Cart.apply_coupon` and then asserts that the patched method returns the patched value. It never runs `apply_coupon`. Deleting the whole method body would still pass. Remove the patch and call the real method with a real `rates` dict. Cover:
   - an active coupon, which returns its rate
   - an inactive or expired coupon, which returns `0.0`
   - an unknown code, which returns `0.0`

6. **`tests/test_cart.py:38-44`** — `test_add_calls_through` patches `Cart.add` and asserts the mock was called once, after the test itself called it. It passes whatever `add` does. Replace it with a test of `add`'s real behavior, or delete it.

### Should fix
7. **`tests/test_cart.py:7` and `tests/test_cart.py:47-49`** — `CART = Cart()` is module-level state shared by five tests. `test_cart_state_after_earlier_tests` asserts `count() == 4`, which holds only if `test_add` and `test_add_multiple` ran first, in file order. The test fails when run alone (`pytest tests/test_cart.py::test_cart_state_after_earlier_tests`) or in reverse order. Selecting tests with `-k` or running in parallel (`pytest-xdist`) will also break it. Use a fixture that builds a fresh `Cart()` per test, and make each test set up the state it asserts on.

8. **`tests/test_cart.py:52-53`** — `test_removing_absent_item` calls `Cart().remove("never-added")` with no assertion. `remove` is documented to return `False` in this case. Returning `True`, or raising `KeyError` (the test would then fail on the exception, not on the wrong value), would go unnoticed, or at best fail only on a crash. Assert `is False`.

9. **Missing cases (the code branches here, no test reaches them)**:
   - `Cart.add` raises `ValueError` when `quantity <= 0`. Nothing tests `0`, a negative number, or the error message. A regression to `< 0` would let `add("x", 0)` through.
   - Adding the same SKU twice should accumulate (`add` returns `_lines.get(sku, 0) + quantity`). Nothing checks it.
   - `count()` on an empty cart, and across multiple SKUs, is untested.
   - `remove` should delete the line entirely. Nothing checks that a second `remove` returns `False`.

10. **Naming** — `test_add`, `test_add_multiple` and `test_remove_returns_something` name the method, not the behavior. For example, `test_add_accumulates_quantity_for_same_sku` and `test_add_rejects_non_positive_quantity` say what breaks when they fail.
