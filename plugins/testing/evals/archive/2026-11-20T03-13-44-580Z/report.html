## Findings

### Blocking
1. **`tests/test_cart.py:11-13`** — `test_add` asserts only `result is not None`. `Cart.add` returns the new quantity for the SKU. A regression that returned `0`, the wrong quantity, or `True` would still pass. Assert `CART.add("widget") == 1` on a fresh cart, and that a second add of the same SKU accumulates.

2. **`tests/test_cart.py:16-18`** — `test_add_multiple` asserts only `count() > 0`. It would pass if `add("widget", 3)` stored 1, 2 or 300 units. The shared `CART` may already hold items from earlier tests, so it would pass even if this `add` did nothing. Use a fresh cart and assert `count() == 3`.

3. **`tests/test_cart.py:21-23`** — `test_remove_returns_something` asserts `remove(...) in (True, False)`, which any boolean satisfies. `remove` could always return `False` and the test would pass. It also never checks that the item was removed. Assert `True` for a present SKU, then `False` and `count() == 0` afterwards.

4. **`tests/test_cart.py:26-27`** — `test_count_is_an_int` checks only the type. `count()` could return `0` or the wrong total, or sum the number of lines instead of units, and it would pass. Assert real totals across several SKUs and quantities.

5. **`tests/test_cart.py:30-33`** — `test_apply_coupon` patches `Cart.apply_coupon` and then asserts the mock returns what the mock was told to return. The real discount logic is never run. It could be deleted or broken and this test would still pass. Remove the patch and call the real method with real `rates`: an active code returns its rate, an unknown code returns `0.0`, and an inactive or expired code returns `0.0`.

6. **`tests/test_cart.py:36-41`** — `test_add_calls_through` patches `Cart.add`, calls the mock, and asserts the mock was called once. It tests `unittest.mock` and nothing in `cart.py`. Delete it, or replace it with a test of real `add` behaviour.

7. **`tests/test_cart.py:8, 44-46`** — The suite shares a module-level `CART`, and `test_cart_state_after_earlier_tests` asserts `count() == 4`. That value only works if `test_add` (+1) and `test_add_multiple` (+3) ran first, in file order. Running the test alone, with `-k`, or in a different order fails it. It also fails if someone adds or removes a test above it. Tests that mutate `CART` then assert on it make every result depend on run order. Give each test its own `Cart()`, for example through a function-scoped fixture, and delete this test.

8. **`tests/test_cart.py:49-50`** — `test_removing_absent_item` has no assertion. It only proves `remove` doesn't raise. The documented behaviour is that it returns `False` when the SKU is absent. Changing it to return `True`, `None`, or to raise `KeyError` for absent items would be caught only in the last case. Assert `remove("never-added") is False`.
