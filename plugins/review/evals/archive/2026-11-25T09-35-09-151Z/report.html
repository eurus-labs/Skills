## Review summary
This change adds `app.py`, an account service with user lookup, order search, login redirect, export download, password hashing, account deletion and receipt formatting. **Verdict: needs work.** The file has several exploitable security holes, and `delete_account` has no authorization check even though its docstring says it does. The file's header and `pyproject.toml` both describe it as an intentionally vulnerable fixture ("DO NOT DEPLOY"). If that is the intent, do not merge it into a deployable branch. I found no rules files (`AGENTS.md`, `CONTRIBUTING.md`, `.github/*`, review checklist), so I checked it against the general standard only.

## Findings

### Blocking
1. **`app.py:28`**: issue: SQL injection (CWE-89) in `find_user`.
   `username` is interpolated into the query with `%`. Passing `' OR '1'='1` returns an arbitrary user row, and `'; DROP TABLE users;--` becomes a stacked-statement attempt.
   Use a parameterized query: `db.execute("... WHERE username = ?", (username,))`.

2. **`app.py:36-38`**: issue: SQL injection (CWE-89) in `search_orders`.
   Both `customer_id` and `status` are f-string interpolated. `customer_id="1 OR 1=1"` returns every customer's orders. `status="x' OR '1'='1"` has the same effect.
   Bind both values as parameters.

3. **`app.py:67-69`**: issue: missing authorization (CWE-862) in `delete_account`.
   The docstring says only an administrator may delete an account that isn't their own, but `actor` is never read. Any caller can delete any account and gets `True` back.
   Check `actor.role == "admin" or actor.id == account_id` before the `DELETE`, and raise or return an error otherwise. Add a test for the denied case.

4. **`app.py:52-54`**: issue: path traversal (CWE-22) in `download_export`.
   `os.path.join(EXPORT_ROOT, filename)` is not confined to `EXPORT_ROOT`. `filename="../../etc/passwd"` reads arbitrary files. An absolute `filename` such as `/etc/passwd` makes `join` discard `EXPORT_ROOT` entirely.
   Resolve with `os.path.realpath`, check that the result is inside `EXPORT_ROOT` (for example with `os.path.commonpath`), and reject it otherwise.

5. **`app.py:16`**: issue: hardcoded secret (CWE-798).
   The session signing key is committed to source. Anyone with repo access can forge session tokens, and the key stays in git history after removal.
   Load it from the environment or a secret store, and rotate this value.

6. **`app.py:59`**: issue: weak password hashing (CWE-327, CWE-328).
   Unsalted MD5 is fast to brute-force, and identical passwords produce identical hashes. A leaked table is cracked with rainbow tables or a GPU in minutes.
   Use `argon2`, `bcrypt` or `scrypt` (`hashlib.scrypt`) with a per-user salt.

### Should fix
1. **`app.py:46-47`**: issue: open redirect (CWE-601) in `login_redirect`.
   `?next=https://evil.example` redirects a freshly authenticated user off-site, which makes phishing links look legitimate.
   Accept only relative paths that start with a single `/` (reject `//` and a scheme), or allow-list the targets.

2. **`app.py:21-31`**: issue: resource leak in `find_user`.
   If `execute` raises, `db.close()` is never reached. Use `contextlib.closing` or `try/finally`.

3. **`app.py:67-68`**: issue: no existence check or rollback.
   Deleting a nonexistent `account_id` still returns `True`, so the caller cannot tell whether anything was deleted. Check `cursor.rowcount`. Also, if `commit` fails, nothing rolls back.

4. **No tests exist**: `detect_stack.py` found no test files (it assumed pytest). The security-sensitive branches above (authorization, path confinement, redirect validation) have no regression coverage.

### Nits
1. **`app.py:34-41`**: nit: `search_orders` takes a `db` argument, but `find_user` opens its own connection. Pick one pattern.
2. **`app.py:77-78`**: nit: `%8.2f` on a float price is fine for display, but money should use `Decimal` if these totals feed anything beyond the printed receipt.

### Questions
1. **`app.py:1-10`**: question: is this file meant to be merged as a deliberately vulnerable fixture, for example for a review-skill eval? If so, it should live under a clearly isolated path such as `tests/fixtures/`, not be importable as application code. If it is real service code, findings 1-6 are all merge-blocking.

- **Schema and migrations:** none exist, so I couldn't check the table or column names.
- **Rules files:** none exist, so only the general standard was applied.
